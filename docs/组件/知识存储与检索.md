# 知识存储与检索

## 发布边界

宿主 Agent 在用户确认后调用一次 `knowledge_publish`，提交 `analysis_id` 与最终选中的原子知识。知识服务从已完成的 Analysis Job 读取来源身份和 EvidenceBundle，整批校验通过后才写入 LanceDB。

每条知识只保存：

- 一个 `stage` 和一个 `knowledge_type`；
- 一个或多个动态 `video_types`；
- 一份可迁移机制正文和正文向量；
- 有效 Evidence Resource 引用、来源分析、置信度和状态。

同义知识由 Agent 检索后显式提交 `existing_knowledge_id`。合并只追加视频类型、证据和来源分析，保留已有正文和向量。

## LanceDB 单库

默认数据库目录为 `~/.video-create/knowledge.lancedb/`；设置 `VIDEO_CREATE_WORKSPACE` 时使用该数据根下的 `knowledge.lancedb/`。`knowledge_units` 表是已发布知识事实、结构化元数据与语义向量的唯一数据库来源；一条知识关联多个视频类型时仍只占一行。

同一数据根只允许一个知识写入者。知识存储写锁覆盖读取待合并行、整批验证、最终行构造以及按 `knowledge_id` 执行一次 `merge_insert` 的全过程，保证并发合并保留每个请求新增的视频类型、证据和来源。

`stage`、`knowledge_type` 和 `status` 使用标量列；`video_types` 使用字符串列表列和 `LABEL_LIST` 索引；正文向量使用固定 512 维浮点向量列。发布和搜索共用随 Plugin 安装的 `BAAI/bge-small-zh-v1.5` 本地模型。

## 检索顺序

`knowledge_list_stage_types(stage)` 先以 `status=active AND stage=<输入阶段>` 过滤 LanceDB 行，再展开 `video_types` 并按视频类型与知识类型去重计数；archived 与其他阶段条目不参与汇总。

创作检索必须同时提交至少一个动态视频类型和至少一个动态知识类型；先在 LanceDB 中预过滤 `active`、阶段、视频类型任意命中和 knowledge type，再按正文向量相似度排序。每个命中返回知识数据与 `similarity`；向量可从同一行的知识正文重建。

精确证据读取通过 Evidence Resource 校验路径和 SHA-256，绕开语义向量检索。
