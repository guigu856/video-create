# 参考学习任务设计

> 本文规定参考视频学习任务的最终产物、Agent 职责、证据边界、知识发布合同与检索方式。

## 1. 任务职责

参考学习任务从真实视频、音频和时间线证据中解释参考片的制作规律，并通过宿主文档能力在当前上下文直接生成和展示一份完整的 DOCX 分析。

插件负责：

- 解析和固化参考媒体；
- 生成帧、联系表、波形、候选边界、节拍候选和分析任务状态；
- 通过 Resource 提供真实证据；
- 保存用户确认的原子知识并生成本地语义向量；
- 按阶段、视频类型、知识类型和语义相似度检索知识。

宿主 Agent 负责：

- 观看和解释真实证据；
- 区分可观察事实与分析判断；
- 通过宿主文档能力直接形成并展示最终 DOCX；
- 从报告中提炼待沉淀知识；
- 根据用户选择调用一次知识发布工具。

参考学习 DOCX 由当前宿主上下文承载。插件持久化确定性证据、分析任务状态和用户确认后的知识；Plugin MCP 的职责集中在证据与知识操作。

## 2. 主流程

```text
reference_resolve_source（输入尚未解析为 SourceMedia 时调用，支持本地与远程）
→ analysis_start
→ analysis_get_job（任务尚未完成时调用）
→ 读取 analysis Evidence Resource
→ analysis_refine_intervals（存在明确证据缺口时调用）
→ knowledge_list_stage_types / knowledge_search（知识分类与去重时按需调用）
→ 宿主 Agent 调用宿主文档能力直接生成并展示六章 DOCX
→ 用户确认全部知识或排除指定编号
→ knowledge_publish（一次原子发布）
```

来源媒体、分析任务和底层证据文件是可恢复的事实状态。EvidenceBundle 根据已持久化 Job 与分析结果确定性构造，不另存一份清单文件。语义分析过程、完整聊天内容和报告正文属于宿主上下文状态。

## 3. 最终分析产物

最终产物是一份连续可读的六章 DOCX。前五章面向没有剪辑和音频工程知识的普通用户，第六章承载 Plugin 的候选知识确认。机器事实由 Analysis Job 与 Evidence Resource 承载；语义结论进入报告，用户确认后的知识进入持久层。

### 3.1 第一章：先用一分钟看懂这条视频

本章依次说明：

1. 这是一条什么视频；
2. 它最主要的一至三个吸引力；
3. 素材、镜头、音乐、文字和效果大致怎样组织；
4. 观众感受如何从开头发展到结尾；
5. 一句话总结。

本章只保留全片主线。具体素材、绝对时间点、坐标、关键帧和引擎参数留在证据或后续创作阶段。

### 3.2 第二章：音乐和声音是怎么带动视频的

本章说明整体听感、音乐段落、重要声音变化、音乐从弱到强及停顿释放的过程，以及音乐强弱如何影响镜头长度和画面变化数量。

使用：

| 时间 | 音乐发生了什么 | 强弱变化 | 画面如何配合 |
| :-- | :-- | :-- | :-- |

| 时间 | 听到了什么变化 | 画面发生了什么 | 带来的感觉 |
| :-- | :-- | :-- | :-- |

内部仍可使用原有音乐结构字段组织数据。前五章正文统一使用“音乐段落”“此时能听到的声音”“重要声音变化”和“音乐强弱变化”。原始 beat、tempo 和瞬态保持候选身份。

### 3.3 第三章：画面是怎么一段段剪出来的

本章先提供连续覆盖全片的简明时间线：

| 时间 | 主要画面 | 画面里的变化 | 对应声音 | 产生的作用 |
| :-- | :-- | :-- | :-- | :-- |

主要画面或叙事承载内容真实改变时才建立新片段。画中画、字幕、遮罩、缩放、位移、旋转、透明度及局部或整体效果写入“画面里的变化”。

再详解最值得学习的重点片段。每个片段写明：

```text
时间
实际看到了什么
画面进行了什么处理
声音如何配合
这种处理带来什么效果
可以学到什么
画面依据
声音依据
把握程度
```

内部仍可使用 `RhythmUnit → MainShot → InShotEvent` 建立关系，但字段名不进入用户可见正文。本章解释参考片实际发生的变化，不承担新素材逐镜执行设计。

### 3.4 第四章：声音和画面是怎么配合的

本章解释当前视频实际使用的关系：

1. 声音和画面同时发生；
2. 画面提前行动；
3. 声音出现后画面再释放；
4. 持续声音连接前后画面；
5. 画面跟随歌词、情绪或音色，而不是机械卡点。

再整理可以重复使用的剪法。每种剪法写明名称、适用场景、操作顺序、观看效果、参考时间、画面依据、声音依据和把握程度。内部可以继续映射 `AudioVisualBinding` 与 `EditingSentence`，用户正文不显示这些字段名。

### 3.5 第五章：如果重新做一条，应该学什么

本章依次说明：

1. 最值得保留的观看体验；
2. 可以直接复用的方法；
3. 不应照搬的人物、素材、绝对时间点、坐标和效果参数；
4. 使用新素材重新创作的步骤；
5. 最终检查表。

重新创作迁移节奏密度、动作关系、声音和画面配合、观看体验及素材选择原则，不复刻原片身份和专属参数。

### 3.6 待沉淀知识

待沉淀知识按“阶段 → 视频类型标签 → 知识类型”组织。一个条目可携带多个视频类型标签，但正文只展示一次，不按标签复制。每条记录包含：

```text
local_id
stage
video_types[]
knowledge_type
content
evidence_refs[]
confidence
existing_knowledge_id（存在同义知识时）
```

用户可确认全部条目，也可排除指定 `local_id`。宿主只向 `knowledge_publish` 提交最终选中的条目。

`local_id` 是单次上下文内的展示编号，使用 `K` 加至少三位十进制数字，例如 `K001`；它不是插件 StableId。`confidence` 只使用 `medium` 或 `high`。

## 4. 证据与判断

关键分析单元分开表达：

```text
实际看到或听到的事实
我们的分析判断
声音依据
画面依据
把握程度
```

内部关键单元可以继续使用稳定编号。用户可见报告优先使用画面帧、声音变化和联系表编号；待沉淀知识引用 `analysis_start` 生成的 Evidence Resource。

原始时间、帧、波形、瞬态和候选边界属于证据。剪辑动机、观看作用、声音解释和可迁移方法属于 Agent 判断。前五章使用“高 / 中 / 低”表示把握程度；只允许中等或高置信度结论进入待沉淀知识。

## 5. Skill 组织

`reference-study` 是参考学习任务的唯一主 Skill，负责：

- 获取和补充证据；
- 在同一上下文中完成语义分析；
- 组织六章最终文档；
- 生成待沉淀知识并处理用户选择；
- 在确认后调用知识发布工具。

以下专业 Skill 只提供观察方法和判断原则：

- `reference-visual-analysis`；
- `reference-bgm-analysis`；
- `audiovisual-relation-analysis`；
- `editing-grammar-synthesis`。

专业 Skill 不生成独立中间报告，不持久化语义结果，也不规定必须填满的分析字段。主 Skill 根据参考片真实特征选用专业方法。

## 6. 知识模型

### 6.1 原子知识

每条知识只表达一个可迁移规律，正文采用以下语义结构：

```text
适用条件 → 剪辑动作或组合机制 → 预期视觉与观看作用
```

知识准入条件：

- 可迁移到其他素材或项目；
- 一条只表达一个规律；
- 至少引用一个关键分析单元或持久证据；
- 正文不包含参考片专属素材名称、绝对时间点、坐标和效果参数；
- 置信度为中等或高。

### 6.2 分类关系

每条知识具有一个 `stage`、一个 `knowledge_type` 和一个或多个 `video_types`。

`video_types` 是知识条目中的动态字符串集合。Agent 先查看当前阶段已有名称，语义相符时复用原名称，没有合适名称时直接提交新名称。视频类型不建立注册表、数据库目录或代码枚举。

`knowledge_type` 由 Rule / Skill 层稳定定义。`reference-study` 主 Skill 包含三阶段发布分类；各创作阶段 Skill 复用所属阶段的同一清单。插件将其作为字符串保存，不在代码和数据库中维护知识类型枚举。

### 6.3 阶段知识类型

| 阶段 | knowledge_type |
| :-- | :-- |
| 阶段一 | `core_mechanism`、`production_method`、`visual_language`、`rhythm_method`、`transition_principle`、`asset_music_traits`、`viewing_experience` |
| 阶段二 | `asset_selection_traits`、`shot_composition_traits`、`action_direction_traits`、`preprocess_need`、`bgm_mood`、`music_sections`、`energy_curve`、`rhythm_events` |
| 阶段三 | `editing_sentence`、`shot_switch_logic`、`layer_composition_pattern`、`motion_pattern`、`effect_scope`、`audio_visual_binding`、`cross_shot_continuity`、`density_pattern`、`transition_pattern` |

同一观察机制服务多个创作阶段时，Agent 为每个阶段分别编写符合该阶段用途的原子知识。多个条目可引用同一证据。

## 7. 知识工具合同

### 7.1 `knowledge_list_stage_types`

输入：

```json
{
  "stage": "stage3"
}
```

工具实时读取该阶段的 active 知识条目，展开 `video_types` 并按视频类型与知识类型去重汇总。archived 条目不进入类型统计。

输出：

```json
{
  "stage": "stage3",
  "video_types": [
    {
      "name": "动漫 MAD",
      "knowledge_types": [
        {"name": "editing_sentence", "count": 12},
        {"name": "audio_visual_binding", "count": 8}
      ]
    }
  ]
}
```

### 7.2 `knowledge_publish`

输入：

```json
{
  "analysis_id": "ANALYSIS_ID",
  "units": [
    {
      "local_id": "K001",
      "existing_knowledge_id": null,
      "stage": "stage3",
      "video_types": ["动漫 MAD", "燃向混剪"],
      "knowledge_type": "editing_sentence",
      "content": "当音乐由连续密集瞬态进入重拍释放时，可先用递进快切积累视觉密度，再切入较长主镜头承接释放，使高潮保持冲击并获得短暂呼吸。",
      "evidence_refs": [
        {
          "resource_uri": "video-create://analysis/ANALYSIS_ID/EVIDENCE_ID",
          "start_ms": 12400,
          "end_ms": 15800
        }
      ],
      "confidence": "high"
    }
  ]
}
```

插件根据 `analysis_id` 读取来源媒体哈希和分析版本，并完成以下机械处理：

1. 验证分析任务与证据归属；
2. 验证每条输入的基本结构；
3. 为新知识生成 `knowledge_id` 和本地语义向量；
4. 为指定 `existing_knowledge_id` 合并新增视频类型与证据；
5. 将整批最终行通过一次 LanceDB `merge_insert` 事务提交；
6. 返回 `local_id`、`knowledge_id` 和 `created | merged` 动作。

合并操作要求 `existing_knowledge_id` 指向 active 条目，且阶段与知识类型和输入一致。插件保留已有正文和向量，只追加去重后的视频类型、证据和来源分析；输入正文不覆盖规范正文。整批输入全部验证通过后才写入。

`evidence_refs` 使用专用 `KnowledgeEvidenceRef`。插件解析 URI 中的 `analysis_id` 与 `evidence_id`，校验证据存在且属于本次分析；`start_ms` 与 `end_ms` 必须同时存在或同时省略。存在区间时满足 `0 <= start_ms < end_ms`，换算为整数微秒后处于来源时长内；EvidenceEntry 声明时间范围时，该区间还必须是其子区间。

用户确认由主 Skill 控制工具调用时机，发布输入不包含确认布尔值、报告路径、报告清单、来源媒体哈希或分析版本。

### 7.3 `knowledge_search`

输入包含：

```text
stage
video_types[]
knowledge_types[]
text
limit
```

检索顺序固定为：

```text
active 状态与 stage 精确过滤
→ video_types 任意一个匹配
→ knowledge_types 匹配
→ content 语义向量相似度排序
```

多个视频类型采用并集语义。每个 `KnowledgeSearchHit` 返回知识正文、阶段、视频类型、知识类型、证据引用、置信度和 `similarity`。

## 8. 存储与向量

LanceDB 是已发布知识及语义向量的唯一数据库。默认数据库目录为 `~/.video-create/knowledge.lancedb/`，使用一个 `knowledge_units` 表同时保存知识事实、结构化元数据和正文向量。每条知识正文只存储一份，`video_types`、`evidence_refs` 与来源分析作为该行的多值数据保存。

同一数据根只允许一个知识写入者。知识存储写锁覆盖读取待合并行、验证整批输入、准备新建或合并后的完整行以及按 `knowledge_id` 执行一次 `merge_insert` 的全过程；应用层同时校验 `knowledge_id` 唯一性。发布和搜索使用同一个固定的本地离线语义 Embedding 模型；每行保存模型名称、模型版本、模型文件校验值、向量维度和正文向量。同一知识只生成一个正文向量；视频类型和证据不进入向量正文。

搜索使用 LanceDB 预过滤：先约束 active 状态、阶段、视频类型和知识类型，再计算正文向量相似度。`video_types` 使用列表字段，并以 `array_has_any` 表达多个请求类型的并集语义。LanceDB 的本地嵌入式连接、单表结构和预过滤能力分别见 [LanceDB Quickstart](https://docs.lancedb.com/quickstart) 与 [Metadata Filtering](https://docs.lancedb.com/search/filtering)。

合法的固定模型版本升级通过知识正文原子重建全部向量，完成后再切换索引元数据。模型文件校验失败、单条向量损坏或实际维度不符时返回稳定错误。单个索引中只使用一个向量空间。

## 9. 持久化边界

持久化内容：

- 来源媒体身份与哈希；
- 分析 Job 状态；
- 帧、联系表、波形、音频与视频算法结果；
- 分析结果、证据文件元数据与文件哈希；
- 用户确认发布的原子知识及本地语义向量。

默认持久数据根为 `~/.video-create/`，`VIDEO_CREATE_WORKSPACE` 可显式覆盖。安装目录和版本化 Plugin 缓存目录不作为默认数据根；来源媒体、Job、分析证据和知识库在 Plugin 更新后继续使用同一数据根。

宿主上下文内容：

- 语义分析过程；
- 六章最终报告；
- 用户尚未确认的待沉淀知识。

参考学习公开流程不包含报告结构校验、报告文件生成和知识发布预览。报告完整性由主 Skill 的分析要求约束，知识输入的机械有效性由 `knowledge_publish` 在写入前统一验证。

## 10. 验收标准

- 一次参考学习通过宿主文档能力在当前上下文形成并展示完整六章 DOCX；
- 没有用户确认时，知识库保持不变；
- 用户可按 `local_id` 排除任意待沉淀知识；
- 一次发布只产生一次工具调用和一个原子事务；
- 一条知识关联多个视频类型时，正文和向量仍只有一份；
- 相同机制跨分析合并时，新增证据和视频类型进入同一 `knowledge_id`；
- `knowledge_list_stage_types` 返回当前阶段的实时汇总；
- `knowledge_search` 按阶段、视频类型和知识类型过滤后执行本地语义排序；
- 参考片时间点、素材身份和效果参数不会进入创作共享知识正文。
