# 参考学习任务调整计划

> 本计划以 `docs/架构/参考学习任务设计.md` 为目标合同，限定参考学习、知识发布和知识检索相关改动。

## 1. 调整结论

现有参考学习实现不符合目标设计。

可直接保留的部分是来源解析、媒体探测、分析 Job、视频与音频确定性证据、区间细化和 Evidence Resource。需要替换的部分是报告合同与文件生成链、知识预览链、知识发布合同、知识分类模型和向量检索实现。

目标主流程为：

```text
reference_resolve_source（输入尚未解析为 SourceMedia 时调用，支持本地与远程）
→ analysis_start
→ analysis_get_job（任务尚未完成时调用）
→ 读取 analysis Evidence Resource
→ analysis_refine_intervals（存在明确证据缺口时调用）
→ 宿主 Agent 调用宿主文档能力直接生成并展示六章 DOCX
→ 用户确认全部知识或排除指定编号
→ knowledge_publish（一次原子发布）
```

`media_probe` 保留为辅助工具，不进入默认主流程。知识分类与去重期间按需调用 `knowledge_list_stage_types` 和 `knowledge_search`。

## 2. 已核实的实现差距

| 范围 | 当前实现 | 目标状态 |
| :-- | :-- | :-- |
| MCP 工具 | `video_create_plugin/mcp/reference.py` 注册 `analysis_validate_artifact`、`report_generate` 和 `knowledge_preview_publication` | 删除这三个公开工具；新增 `knowledge_list_stage_types`；重定义 `knowledge_publish` 和 `knowledge_search` |
| 主 Skill | `skills/reference-study/SKILL.md` 要求报告 Schema、校验、文件生成和发布预览 | Agent 读取证据后通过宿主文档能力直接生成并展示六章 DOCX，确认后只调用一次发布工具 |
| 专业 Skills | 已包含局部观察规则，但没有完整统一 `RhythmUnit → MainShot → InShotEvent`、独立 BGM 时间线和候选知识准入规则 | 四个专业 Skill 只提供分析方法，由 `reference-study` 统一归并结果 |
| 报告实现 | `video_create_plugin/reporting` 保存报告模型、校验器、JSON/DOCX 生成器和 Manifest；`validation/reference_study` 再次组装整条报告链 | 只保留 EvidenceBundle 构造能力并归入分析模块；移除报告文件与 Runner 链 |
| 知识合同 | `KnowledgeUnitDraft` 使用多阶段、固定知识类型枚举、报告 Manifest、确认布尔值及多组检索标签 | 一条知识只有一个阶段、一个知识类型、多个动态视频类型和一个正文；发布只接收 `analysis_id + units` |
| 发布行为 | 发布前重新读取 Manifest 和报告，并重复执行 Preview 校验 | 单次发布从 `analysis_id` 取得来源身份，机械校验证据归属，并在一个事务内创建或显式合并 |
| 视频类型 | 当前使用 `video_type_tags`，检索要求请求标签全部命中 | 保存为动态 `video_types[]`；多个请求类型采用任意命中语义 |
| 知识存储与向量 | `video_create_plugin/knowledge/store.py` 使用关系表保存知识并计算 128 维字符哈希向量 | 使用 LanceDB 单库保存知识事实、结构化元数据和正文向量；发布与搜索共享固定的中文本地语义模型与同一向量空间 |
| 类型发现 | 当前没有阶段类型实时汇总工具 | `knowledge_list_stage_types(stage)` 直接汇总已有知识，不建立类型目录或注册表 |
| 持久数据根 | `create_server()` 默认使用当前工作目录，安装后可能落入版本化 Plugin 缓存 | 默认使用 `~/.video-create/`，并允许 `VIDEO_CREATE_WORKSPACE` 显式覆盖 |
| 测试与文档 | 当前测试和组件文档保护 Report、Manifest、Preview 与固定分类 | 测试和文档只描述最终工具流、宿主上下文 DOCX 及单次知识发布 |

## 3. 目标代码边界

### 3.1 分析模块

将以下内容归入 `video_create_plugin/analysis`：

- `EvidenceEntry`；
- `EvidenceBundle`；
- `build_evidence_bundle`；
- Evidence Resource 的读取与文件哈希校验。

分析模块继续保存可复现事实，不保存六章语义报告和 Agent 分析过程。EvidenceBundle 根据持久化 Job 与分析结果确定性构造，不额外写入 `evidence_bundle.json`。

### 3.2 知识模块

`video_create_plugin/knowledge/models.py` 只保留目标合同需要的数据：

```text
KnowledgeUnitDraft
├─ local_id
├─ existing_knowledge_id?
├─ stage
├─ video_types[]
├─ knowledge_type
├─ content
├─ evidence_refs[]
└─ confidence

KnowledgeEvidenceRef
├─ resource_uri
├─ start_ms?
└─ end_ms?

KnowledgePublishRequest
├─ analysis_id
└─ units[]
```

已发布知识增加插件生成的 `knowledge_id`、来源分析身份、状态、创建时间及向量元数据。知识类型和视频类型均按字符串保存；代码只校验非空、去重和基本长度，不维护分类枚举。

`video_create_plugin/application/knowledge.py` 负责一次发布的应用逻辑：

1. 读取已完成的 Analysis Job 和 EvidenceBundle；
2. 校验每个证据 URI、证据 ID 和可选时间范围属于请求中的 `analysis_id`；
3. 校验 `local_id` 符合 `^K[0-9]{3,}$` 且批内唯一，字段完整，置信度为 `medium | high`；
4. 新条目生成 `knowledge_id` 和正文向量；
5. 带 `existing_knowledge_id` 的条目先校验目标存在、状态有效、阶段与知识类型一致，再只合并视频类型、来源证据和分析来源；
6. 在全部输入通过后执行单个 LanceDB `merge_insert` 事务；
7. 返回每个 `local_id` 对应的 `knowledge_id` 和 `created | merged`。

`KnowledgeEvidenceRef` 解析 `video-create://analysis/{analysis_id}/{evidence_id}`。`start_ms` 与 `end_ms` 同时存在或同时省略；存在时满足 `0 <= start_ms < end_ms`，乘以 1000 后按整数微秒校验来源时长，并在 EvidenceEntry 提供时间范围时校验为其子区间。未知证据、跨分析引用和越界区间使整批零写入。

插件不根据向量相似度自动合并知识。语义去重由 Agent 先检索，再显式提交 `existing_knowledge_id`。合并时保留目标条目的正文和向量，输入正文不覆盖规范正文。

### 3.3 存储模块

LanceDB 是知识模块的唯一数据库。默认数据库目录为 `~/.video-create/knowledge.lancedb/`；设置 `VIDEO_CREATE_WORKSPACE` 时使用该数据根下的 `knowledge.lancedb/`。数据库使用一个 `knowledge_units` 表，每条知识正文、结构化元数据和向量只保存一份。目标数据关系为：

```text
knowledge_units
├─ knowledge_id
├─ stage
├─ knowledge_type
├─ content
├─ video_types[]
├─ evidence_refs[]
├─ provenances[]
├─ confidence
├─ status
├─ embedding_model
├─ embedding_version
├─ embedding_sha256
├─ embedding_dimension
└─ vector
```

`stage` 与 `knowledge_type` 使用单值字符串列；`video_types` 使用字符串列表列；`evidence_refs` 与 `provenances` 使用列表结构列。数据库中不建立视频类型目录表、知识类型目录表或多阶段关联表。

首个实现锁定 `lancedb>=0.36,<0.37`。同一数据根只允许一个知识写入者；知识存储写锁覆盖读取待合并行、整批验证、最终行构造和 `merge_insert` 提交。LanceDB 的 merge key 不执行唯一性约束，因此应用层在事务前校验库内与批内 `knowledge_id` 唯一。`merge_insert` 的事务语义见 [LanceDB Python API](https://lancedb.github.io/lancedb/python/python/#lancedb.table.Table.merge_insert)。

`knowledge_list_stage_types(stage)` 先在 LanceDB 中以 `status=active AND stage=<输入阶段>` 过滤知识行，再由应用层展开 `video_types`，按视频类型和知识类型去重计数；archived 与其他阶段条目不参与汇总。`knowledge_search` 使用 LanceDB 预过滤，依次应用状态、阶段、`array_has_any(video_types, ...)` 和知识类型条件，再执行正文向量相似度排序。`video_types` 建立 `LABEL_LIST` 标量索引；阶段、知识类型和状态建立适用的标量索引。

搜索输出使用 `KnowledgeSearchHit`，每项包含知识数据与 `similarity`。archived 条目不进入类型统计和默认搜索。

### 3.4 本地语义向量

首个实现固定使用 FastEmbed 0.8.x 与 `BAAI/bge-small-zh-v1.5`，向量维度为 512。模型文件随 Plugin 安装包进入 `video_create_plugin/assets/models/bge-small-zh-v1.5/`，运行期只从该目录加载，不执行联网下载，也不提供模型切换配置。

依赖版本与 Python 要求以 [FastEmbed 的 PyPI 元数据](https://pypi.org/project/fastembed/) 和 [LanceDB 的 PyPI 元数据](https://pypi.org/project/lancedb/) 为准；模型语言、维度和文件规模以 [FastEmbed 官方支持模型清单](https://qdrant.github.io/fastembed/examples/Supported_Models/) 为准。

实现使用一个具体的本地嵌入服务，不建立 Provider 抽象。FastEmbed 通过 `specific_model_path` 指向 Plugin 模型资产，并启用 `local_files_only`。索引元数据保存模型名、固定版本、模型文件校验值和向量维度。余弦计算要求查询向量与存储向量维度完全一致。

固定模型发布升级时，服务根据知识正文原子重建全部向量，成功后更新索引元数据。模型资产校验失败、单条向量损坏或实际维度不符时返回稳定错误。

实现阶段直接建立 LanceDB 目标结构，不建立第二套知识事实库、向量索引或双写同步路径。

已安装 Plugin 的默认持久数据根固定为 `~/.video-create/`，现有 `VIDEO_CREATE_WORKSPACE` 继续作为显式覆盖。`create_server()` 不再把当前工作目录作为默认数据根；版本化 Plugin 缓存目录只承载代码和静态资源。来源媒体、Analysis Job、证据和 `knowledge.lancedb/` 共用稳定数据根。

## 6. 完成标准

- MCP 中不存在 `analysis_validate_artifact`、`report_generate` 和 `knowledge_preview_publication`；
- 宿主 Agent 在读取证据后通过宿主文档能力直接生成并展示六章 DOCX；
- 插件不会生成或保存参考报告文件、Manifest 和报告快照；
- EvidenceBundle 由持久化 Job 与分析结果确定性构造，不产生重复清单文件；
- 默认持久数据根不随 Plugin 安装版本变化；
- `knowledge_publish` 只接收 `analysis_id` 与最终选中知识，并以一个事务完成整批发布；
- LanceDB 是已发布知识事实、元数据和向量的唯一数据库；
- 一条知识只有一个阶段、一个知识类型、多个动态视频类型、一份正文和一份向量；
- 跨分析合并必须显式携带 `existing_knowledge_id`；
